# Codex development agent catalog

These 24 repository-local profiles develop Engineering Studio. They are not the app’s eight developer bots, do not create running instances, and do not imply a connected executor. The duplicate Visual Storyteller request is installed once.

The upstream converter ran successfully on all selected sources. Its role identity and mission were then adapted for native Swift implementation, current user instructions and focused collaboration. Unrelated stacks, compulsory ceremonies and unsupported performance/readiness claims were removed. Names use source filenames so every role remains unambiguous. Models and reasoning effort inherit the parent.

## Selection and ownership

Use the smallest team needed for the task. The orchestrator assigns exact files, acceptance criteria and dependencies; broad path descriptions below identify expertise, not automatic write permission. Parallel edits require disjoint file ownership. Read-only review may overlap implementation; shared-file changes must be serialized or transferred.

## Handoff contract

Every handoff includes the outcome/task identifier, base/head commit when available, owned files and symbols, changed contracts, acceptance status, exact checks and evidence paths, known failures, next owner and next action. The receiving role verifies the evidence before building on the result. Credentials never travel in task context.

Typical flow: Product Manager frames the outcome; Master Plan Architect scopes delivery; Software Architect and UX Architect define the relevant contracts; focused engineers implement disjoint changes; Reality Checker independently verifies the result; Git Workflow Master integrates only within current authorization. Workflow Architect defines behavior, Multi-Agent Systems Architect defines runtime coordination, and Agents Orchestrator coordinates Codex development work. These are separate responsibilities.

The parent session controls permissions. Profiles neither add approval checkpoints nor grant authority for external messages, publishing, merges or account changes. Blocked roles report a precise dependency and continue independent work where possible.

## Installation and provenance

Profiles are installed in `.codex/agents/` using the standalone custom-agent TOML schema: `name`, `description`, `developer_instructions`. [Project configuration](../.codex/config.toml) also explicitly registers all 24 roles through `[agents.<role>]` and `config_file`; instructions are stored once. This follows the official Codex config schema and supports clients that do not expose standalone discovery.

Local registration was verified with `codex-cli 0.159.0-alpha.3`: the read-only app-server `config/read` endpoint returned all 24 profiles and concurrency 8, and every referenced file resolved to the matching name, description and instructions. The reviewed checkout was trusted in the local CLI configuration without changing approval or sandbox policy; another machine must establish its own project trust. No model call or agent spawn was used for verification. Reload the Codex project/session to consume the configuration. This does not hot-register new agent types in an already-running hosted chat or prove runtime execution.

[Conversion manifest](agency-provenance.json) records the pinned upstream commit, source and generated-output hashes, exact conversion command and adaptations. [MIT attribution](licenses/agency-agents.txt) is retained. No upstream source was unavailable.
